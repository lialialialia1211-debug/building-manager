# Web 原型玩家測試

## QA 環境硬性規則

- 所有真人／人工 QA 一律使用 GitHub 提供的線上預覽網址。
- 禁止使用 localhost、本機開發伺服器、`file://` 或本機 production build 進行人工 QA。
- 本機只可執行自動化測試、validator、build 與開發診斷。
- 開始測試前必須記錄 GitHub 預覽網址與部署 commit，並實際開啟網址確認可操作。
- 若尚無可用的 GitHub 線上預覽網址，本輪人工 QA 狀態必須標記為 `BLOCKED`，不得改以本機測試替代。

## 人數

- 第一輪：5 人。
- 第二輪：至少 5 人，且不得全部與第一輪相同。

## 測試前準備

- 記錄測試日期與 build commit。
- 記錄 GitHub 線上預覽網址，並確認該網址部署的 commit 與本輪 build commit 相同。
- 每位測試者使用獨立的結果表。
- 確認瀏覽器可使用 localStorage。
- 不要求姓名、聯絡方式或其他個人資料。
- 不開啟開發者用 panel ID 標示。

## 流程

1. 不解釋結局條件，只說「從 12 張畫面中挑 6 張，拖進漫畫頁；確認前可以換位」。
2. 由測試者先玩任一房間到結局，主持人記錄完成時間。
3. 詢問是否願意立即重玩；分別記錄自發重玩與受邀後重玩。
4. 完成另一房間，並記錄該房間完成時間與到達結局。
5. 在兩房各抽一組 12 張候選牌局，請測試者逐一口述卡片行動意圖，並選出六張最容易區分的卡；主持人只記錄辨識答案，不記自由對話內容。
6. 請測試者查看結果、大樓與圖鑑，觀察是否理解共同謎團與解鎖關係。
7. 開啟設定，請測試者明確按下「匯出玩家測試 JSON」。
8. 確認 JSON 由瀏覽器下載；不得以網路、背景程序或自動上傳傳送紀錄。

## 必問問題

- 哪一次選擇最難判斷？為什麼？
- 結果是否與候選畫面合理相關？
- 第一次完成後是否想找其他結局？
- 數值提示太多、太少或剛好？
- 大樓共同謎團是否足以讓你想玩正式版？

## 主持人觀察

- 每個房間從開始到結局的時間。
- 測試者完成 12 選 6 編排所需時間、換位次數、移除次數，以及是否理解「確認後才鎖定」。
- 候選圖是否能在沒有 raw panel ID 的情況下辨識。
- 測試者是否在未受邀前主動選擇重新遊玩。
- 美術角色、空間、道具、光線與漫畫格之間的不一致。
- 最常造成停頓、誤解或錯誤預期的前三個位置。
- 下一輪測試前必須完成的變更。

## 資料處理

- `building-manager-playtest-v1` 僅存在測試裝置的 localStorage。
- JSON 只能由測試者或主持人明確按下匯出按鈕後下載。
- 紀錄只含匿名 session ID、時間、畫面與穩定產品 ID／數字。
- 不記錄對話文字、角色自由文字、使用者輸入、IP、瀏覽器指紋或個人資料。
- 測試結束後由主持人依團隊既有安全流程保管下載檔；原型不會自動清除本機紀錄。
